## 1. 已确认的需求与非目标

### 1.1 必须满足

1. 真正整改 WebView JavaScript 与信令缺少证书 pinning 两项新增告警，不 dismiss、不排除查询、不更换写法绕过分析器。
2. 优先复用既有节点—管理中心链路，不默认引入新的公共信令服务，不要求已注册用户再部署服务器或填写服务地址。
3. 用管理中心辅助建连，不等于允许管理中心持续转发业务数据；TURN、mailbox、`peer.rpc` 等数据中继分别受原有权限和明确授权控制。
4. 用户真实服务器域名只在受控 GitHub 打包阶段注入，不能出现在公开源码、工作流文本、构建日志、Job Summary、测试报告或公开源码包中。
5. 保留现有配对身份、内容密钥、业务权限、撤销检查和短信幂等语义。
6. 实施、CI 配置变更、服务器升级、提交和推送均须另行批准；无论如何不得自动合并 main。

### 1.2 域名保护的准确边界

用户已选择“源码和日志不泄露”，不是“对 APK 或运行中的终端隐藏域名”。因此：

- GitHub Secrets 的存储保护、构建输入隔离、HTTPS/TLS 传输加密是实际防护；Base64、字符串拆分、把 AES 密钥同时打入 APK 都不是可靠保密机制。
- 带真实配置的 APK 需要知道端点，可以被逆向、解包或动态观察得到域名。该 APK 是允许携带配置的明确例外，不能要求它同时通过“绝不含真实域名”的检查。
- 域名可能被 DNS、TLS 元数据、证书透明度日志、终端调试和服务访问观察发现；不承诺域名具有匿名性或不可发现性。
- 不在本轮引入“注册后解密域名”或自定义密码算法，也不将域名当作访问控制手段。服务仍须认证、限流和最小权限。
- 本文及公开仓库只使用保留示例域名 `node.relay.invalid`、`admin.relay.invalid`；不索取、读取或记录真实值。

### 1.3 零配置的适用范围

“零额外配置”指已有节点注册、已有管理中心账户/会话及合法配对关系的用户。首次认证、首次信令授权、证书信任迁移和必要的本地解锁不是可跳过的步骤。

完全独立且未接入任何管理中心的 P2P 用户没有可复用链路：保留可用的局域网直连；本设计不承诺其公网自动发现，不暗中使用 PeerJS 或新托管服务作为回退。

## 3. 架构与完整流程

```text
已认证控制端                        既有管理中心                        已注册 SIM 节点
  控制端会话 + CSRF      ───►     信令专用路由/有界队列      ◄───      Device token
  配对身份签名 + 信令密文         不持有配对内容密钥                    配对身份签名 + 信令密文
            │                         │                                  │
            └────────────── 加密 OFFER / ANSWER / ICE ─────────────────────┘
            │                                                            │
            └════════════ 原生 WebRTC DataChannel + 既有业务 AEAD ═════════┘
                         默认 LAN / DIRECT，不自动启用 TURN
```

1. 双端完成既有注册/登录与 P2P 配对，具备各自独立凭据、配对身份和密钥。
2. 用户启用“使用已关联管理中心辅助直连”。复用已有地址和账户；缺控制端会话时走正常登录，不共享节点 token，不偷偷创建管理员会话。
3. 验证管理中心 TLS 信任配置、节点注册身份、P2P 身份对应关系和双方信令授权。注入的地址与二维码 hint 本身均不授权。
4. 控制端和节点用各自认证入口建立一个限时、限定配对、仅用于信令的会话。
5. 原生 RTC 产生 SDP/ICE；客户端使用用途分离的信令密钥加密后交中心投递，对端校验会话、方向、序号和有效期后才交给 RTC。
6. DataChannel 建立后，由实际选中候选对确认 LAN/DIRECT/TURN，不能用“信令连接成功”冒充数据通道在线。
7. 业务继续经既有 `PeerProtocol` 和 `PeerRpc` 处理。只完成信令授权的配置，保持 `P2P_ONLY` 且拒绝 TURN/mailbox/Legacy Relay 业务传输。
8. 首次 ICE 收集、必要候选交换结束后关闭临时信令会话并清理队列；既有节点到中心的常规同步不因此停止。后续重连另建短会话，不永久保存 SDP/ICE。

加密信令不隐藏中心可见的节点注册关系、绑定公钥/配对关系、IP、时间、流量大小和投递元数据；双方也会获知必要 ICE 候选。中心不持有内容密钥与“中心不知道任何关系/地址”是不同承诺，本设计只作前者。

## 4. 身份、权限和 API 契约

### 4.1 绝不混用的三层权限

| 层 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 节点 Device token | 某注册节点可访问其节点路由 | 不能调用管理路由，不能授权任意 P2P 控制端 |
| 控制端会话及 CSRF/本地解锁 | 控制端可访问所获管理权限范围 | 不等于持有对端配对密钥，不自动获得持续数据中继权 |
| P2P 配对身份/密钥及每对授权 | 可与该配对对端建立受认证通道 | 不等于同意中心承载短信内容，即便是密文 |

节点凭据不出节点；控制端 Cookie 不发给节点；配对内容密钥不发给管理中心。新接口不能通过共享 Admin Token、公开服务账号或把节点 token 放进 APK/二维码解决授权问题。

### 4.2 新增信令授权状态，独立于业务路由

拟新增每对本地字段：`signalingConsent`、`signalingCenterBinding`、`signalingConsentRevision`；具体存储升级由实施计划定义。

- 用户动作只授予中心辅助建连，不设置 `fallbackConsent`、`relayBindingState` 或改写 `policy`。
- 节点端只接受本机已配对且获允许的控制端。中心会话不能替代节点的配对授权。
- 服务端注册绑定由节点凭 Device 身份提交，并证明其 P2P 公钥持有权；同时维护被允许的配对控制端身份/授权修订。不能仅信任控制端上传的任意 deviceId/publicKey。
- 控制端请求既须合法管理会话，也须证明其配对私钥持有权，并与上述节点授权匹配；若现有会话不能提供所需节点范围，必须补充显式校验，不能假定全局管理员会话天然满足最小权限。
- 会话创建签名覆盖用途、中心标识、nodeId、配对双端身份、会话 ID、挑战、有效期、授权修订及协议版本，防跨中心或跨用途重放。
- 撤销配对、节点注册、控制端权限或信令授权，应使对应会话及待投递信令立即失效；处理已到达的排队回调前也要复查。

绑定注册的最小契约拟为：节点凭 Device 认证获取一次性、最长 60 秒挑战，提交 `protocolVersion`、`bindingId`、`nodeId`、`nodePublicKey`、`allowedControllerPeerId`、`allowedControllerPublicKey`、`consentRevision`、`allowed`、`challengeId`、`expires`、`signature`。`bindingId` 首建时省略并由服务端随机生成，后续更新/撤销必须提供且属于同一节点与配对；各阶段统一使用这个字段名。每次请求只处理一个配对绑定，身份摘要必须与公钥一致，nodeId 必须与 Device 认证一致；撤销使用更高修订的 `allowed=false`。服务端验证节点持钥证明、单次挑战与单调修订，返回 `bindingId`、`acceptedRevision`、有效期和协议版本，不返回或修改业务策略。控制端建立会话时提交匹配的 bindingId、控制端持钥证明和其合法会话。

失败语义至少区分认证失效、配对绑定不匹配、挑战过期/复用、修订过旧、协议不支持及限流；外部响应不泄露其他配对的存在。签名编码必须明确字段类型、顺序和长度前缀并提供双语言测试向量。既有 `PeerCrypto.sign/verify` 内置业务 domain，不能未加用途标签直接复用；拟新增显式信令用途的签名入口，不修改原业务签名前缀而破坏兼容。

### 4.3 路由建议

在既有 `/api/v1` 的 controller/node 安全表面上分别新增信令专用 routes，语义为 session create、signal send/poll/ack、session close。名称可采用 `peer-signaling`，最终路由需与现有鉴权中间件共同审核。

- 不调用 `PeerRelayTransport.request()`，不装入 `peer.rpc`，不进入 `PeerRpc.dispatch()`。
- 优先独立有界队列，避免依赖命令加密的 Global Vault 解锁以及短信 ACK/副作用状态机。
- 如实施时拟复用节点命令轮询载体，必须显式新增独立 `peer.signal` 分支并证明其无业务副作用；它不是可以默认为等价的替代方案，须再次审核。
- 控制端 Cookie 路由保持 CSRF 防护；节点路由保持 Device token 校验。管理域与节点域若已分离，继续分离，不为省配置合并安全表面。
- 新路由须同步登记 `simhub_server.py::is_device_route()` 及现有 Host/方法白名单，验证 `SEPARATE_SURFACES` 开启后的两侧正/负用例。两表面使用同一受控信令存储；单进程同库可沿既有部署，若多进程/分离实例则必须证明共享事务/撤销状态，不能使用互不可见的进程内队列。
- 服务端响应不得携带客户端业务策略修改指令；权限变化只能走独立、可审计的用户授权操作。
- 背景信令不能延长管理会话空闲有效期。会话失效时显示 `AUTH_REQUIRED`，等待正常重新认证。

## 5. 信令协议与资源限制

### 5.1 用途分离

业务 `PeerProtocol` 线格式和内容密钥保持不变。新信令采用独立 `PeerSignalingProtocol`，从配对根密钥以 HKDF-SHA256 和固定用途标签 `simhub-peer-signal-v1` 派生信令子密钥；不复用业务 AEAD 的密钥/nonce 空间。

外层仅保留投递所需字段：版本、固定信令 domain、随机 sessionId、随机 messageId、方向、序号、有效期、授权修订、nonce、密文。它们全部进入 AEAD AAD；不允许只把 domain 放在 JSON 外层而不认证。

密文只允许 OFFER、ANSWER、ICE、END_OF_CANDIDATES、CLOSE；字段严格校验，拒绝 `read/history/state/send/peer.rpc` 等 RPC 内容。消息 ID/序号去重与有效期校验由接收端执行，不能只相信服务器。

新信令协议与业务协议使用独立 parser、domain、派生用途和测试向量，互换密文必须失败。SDP 指纹和 ICE 内容在认证解密成功后才能交给原生引擎。

### 5.2 首版目标上限

下列是拟实施的保守默认值，需用真实 data-only SDP/ICE 用例验证；不通过测试不得放宽后直接发布。

| 项 | 上限/策略 |
| --- | --- |
| 信令会话 | 最长 300 秒，不因普通轮询无限续期 |
| 单条信令 | 最长 120 秒，且不得超过会话有效期 |
| 单帧 | 64 KiB，包括编码后的外层 |
| 每会话每方向 | 最多 32 条未 ACK 帧、2 MiB；ACK 后仍保留本会话去重记录 |
| 节点并发 | 最多 2 个活动建连会话，避免重连风暴 |
| 全局队列 | 64 MiB，有界拒绝，不驱逐其他节点的有效会话来容纳攻击流量 |
| 速率 | 每对每方向最多 60 帧/分钟、每节点最多新建 10 会话/分钟，并叠加现有 IP/身份限流 |
| 存储 | 密文与必要元数据；过期/关闭/撤销时删除，重启不恢复过期授权 |

服务端只 ACK“已接收/投递的信令”，绝不表示业务已执行。待重传帧维持相同 ID，接收端拒绝重复处理；同 ID 不同密文/内容应拒绝。严格限制输入深度、字符串长度、并发和解析消耗。

这些是新信令队列的独立预算，不继承 `peer_connect.py` 的 128 MB 全局 mailbox 配额，也不与现有业务队列共享计数来意外扩大容量。

## 6. 原生 WebRTC 迁移

### 6.1 保持的边界

新增原生 RTC 传输实现，继续满足 `HubTransport.request/route` 及调用方需要的 `init/signal/restart/online/close` 语义。具体类名允许采用 `PeerNativeRtcTransport`，不为保留旧名称而假装仍有 bundled script。

- DataChannel 仅传输既有加密业务帧，不新增音频、视频轨或采集权限。
- 单一串行执行域协调信令与状态，明确 native callback 的线程、关闭竞态、过期回调和对象释放；不机械照搬 WebView 的主线程约束。
- ICE selected candidate pair 的真实统计用于 LAN/DIRECT/TURN 判定；未知路由不能默认视为 DIRECT。
- `online` 仅表示数据通道可用，不是中心会话在线或引擎初始化完成。
- 网络切换重建 ICE/必要时引擎；请求超时、取消、close 必须完成所有 pending futures，避免重复业务执行和 native 泄漏。
- 默认服务器配置只允许经审批的 STUN；不因信令响应而擅自接受 TURN。存在私有 STUN/TURN 主机时，同样不得硬编码进公开源码。

### 6.2 依赖决策门槛

已核实有第三方维护的 Maven Central AAR 候选 `io.github.webrtc-sdk:android`，不是 Google 官方发行承诺。本轮未下载/安装 AAR、未构建。

选定版本前必须核实：源码 commit 与发布产物对应、签名/校验与许可证、已知安全问题、minSdk 29、目标 ABI、16 KiB 页大小支持、R8/JNI 规则、APK 体积与 cold-start/内存。版本固定，不使用 `+`/动态版本；审核构建插件和传递依赖。

原生 AAR 是阻塞性外部依赖：若可信来源、构建/ABI/性能或安全验证不成立，原生迁移不能进入发布，需重新选型；不能回退 WebView 然后声称两项告警已解决。新 AAR 同样可能引入新的供应链风险和分析告警，必须纳入门禁。

先在假端点/本地沙盒证明 data-only 互通，再接中心信令。迁移完成后移除对应 WebView、资产、桥接及“脚本已加载”测试；其他模块若仍使用 AndroidX WebKit，不顺带删除其依赖。`PeerCloudConnector` 的未 pin PeerJS 网络调用必须从扫描源集中删除（可删除整类或移除该调用并接入新实现），仅“不再调用/标为退役”不足以消除静态告警；同理旧 WebView JS sink 不能以保留闲置源码的方式存在。

## 7. 管理中心的 TLS pinning 与可信引导

### 7.1 主信任模型

首版采用平台 CA/有效期/主机名验证，加受测共享 HTTP client 上的 SPKI SHA-256 pin 校验，本方案选择 OkHttp 实现。**现有 `ApiClient.raw()` 与 `ControllerSecureClient.request()` 使用的是 `HttpURLConnection`，不能直接挂载 `CertificatePinner`。**本设计明确选择将这两处底层 JSON HTTP 请求适配到共享、受测的 OkHttp 工厂；保持其上层方法、节点 token/控制端 Cookie、CSRF、超时、响应大小限制、错误码和 token 轮换契约不变。不是假定当前已使用 OkHttp，也不扩展成整个应用的无关网络重构。

对已绑定可信配置的中心，两角色的认证/注册/业务及新信令 JSON 请求均应走该受测工厂，避免仅新信令有 pin、同一凭据却在另一条旧路径发送。需要盘点所有入口并做合同回归；漏迁移承载相同中心凭据的入口即阻止启用新功能。不具备可信 pin 的旧 origin 不能用于新辅助建连。下载器等不承载这两角色认证的网络路径不在本轮顺带重构。

对每个精确域名配置当前与独立备用公钥，不全局放宽 TrustManager，不混搭私有 CA 来假装公共 ACME 证书受其签发。如果实施时不接受上述受限迁移，须先重新审核一个针对实际 `HttpsURLConnection` 握手生效的替代方案；不能事后读取服务器证书、请求已发出后才检查 pin，也不能暗中换成自定义宽松校验。

运行时必须同时验证：HTTPS、规范化的精确 origin（scheme/host/port）、禁止 userinfo/query/fragment、预期 API 路径、无跨 origin 重定向、至少两个合法且不同的 pin。OkHttp 对无匹配域名默认不做 pin 校验，因此业务层必须显式拒绝“端点没有匹配 pin”，不能只构造一个非空 pinner。

仅覆盖新 connector 不够：被复用的 `ApiClient` 节点请求与 `ControllerSecureClient` 控制端请求，凡承载新信令和凭据的实际 TLS client 都必须采用同一受审核配置。不能创建一个有 pin 的闲置 client 来让 CodeQL 变绿。

### 7.2 两个可信配置入口

**专用私密构建（优先）：**真实 origin 与双 pin 通过受控 GitHub 打包注入，信任随应用签名分发。既有已注册 origin 必须与配置精确匹配；不匹配时明确提示，不覆盖用户配置或把 bearer 发到新 host。

**通用构建/其他合法自托管中心：**扩展可信注册/管理中心 QR 描述，携带 origin、角色对应的 pin 集合、配置版本及有效约束。二维码必须由运营方掌握 TLS 公钥的配置生成，不是客户端首次连接后抓取证书生成。二维码交付本身需已有可信渠道或线下核验；任意网络二维码的自签名不能独自证明它属于预期管理中心。

现有 controller link 仅解析 URL，节点注册 QR 依赖一次性注册材料，二者都没有可直接沿用的二维码签名。新增 pin 描述的初始真实性明确依赖上述可信交付/线下核验；P2P 配对二维码已有的身份签名只能绑定“双方选择了同一份描述”，不能凭空证明管理中心归属。若后续要求远程全自动可信导入，则必须另设预置信任锚和经过审核的签名描述协议，不能在实施中假定旧 QR 已提供。

现有注册 QR 和 controller link 没有 pin 字段，此路径需要版本化扩展。`relayHint` 仍只作提示；它既不能覆盖注入的 pin，也不能自动建立中心授权。

对于已安装但没有可信 pin 的旧注册，不做静默 TOFU 迁移：匹配的专用构建可直接使用其预置 pin；其他部署需可信配置更新/新 QR。该安全迁移可能需要一次用户操作，不能承诺对所有旧客户端绝对无感。

### 7.3 续期、换钥和恢复

1. 预先安全生成 current/backup 两把独立 TLS key；私钥不进入公开仓库或客户端，打包作业只需 origin 和公钥哈希。
2. 普通证书续期若保留同一公钥，可不改变 pin；必须确认实际 TLS 终结点行为，不能假设 Caddy、CDN 或 ACME 工具默认保留 key。
3. 换钥前，先发布覆盖新 key 的客户端；验证部署覆盖率和备用证书演练，再切服务端。
4. 随后通过应用更新撤销退役/泄露 key 并补充新 backup。旧客户端无限期不更新时不保证可用；密钥泄露后的旧 pin 也不能凭服务端切钥自动撤销。
5. pin 不匹配或可信配置过期时 fail-closed，不使用任何 pin expiration/静默降级机制自动停止校验，不自动退回未 pin 路径。
6. 恢复依靠可信应用更新/可信新 QR，不从验证失败的连接获取新 pin 后信任。独立签名 pinset、反回滚和免发版更新留待后续单独设计，不作为首版隐含依赖。

## 8. GitHub 打包时注入真实域名

### 8.1 配置形状与 Secrets

不在源码、GitHub Variables、命令参数、workflow input 或 PR 评论中传真实值。建议使用受保护 Environment `p2p-private-packaging`，以下名称仅为未来配置建议：

| Secret | 内容 |
| --- | --- |
| `P2P_NODE_ORIGIN` | 既有节点安全表面的精确 HTTPS origin |
| `P2P_NODE_PIN_CURRENT` / `P2P_NODE_PIN_BACKUP` | 该 TLS 终结点的两枚 SPKI SHA-256 pin |
| `P2P_CONTROLLER_ORIGIN` | 既有管理安全表面的精确 HTTPS origin |
| `P2P_CONTROLLER_PIN_CURRENT` / `P2P_CONTROLLER_PIN_BACKUP` | 该 TLS 终结点的两枚 pin |

两个角色若确实共用一个 origin，也显式校验一致性；若既有部署分离两个 origin，绝不为复用信令合并它们。Secret 一值一项，避免把整个敏感 JSON 作为日志脱敏依赖。

生成的 APK 内部配置包含 schemaVersion、非敏感且随机生成的 configId、两个角色 origin/pins。configId 不以域名摘要充当，因为低熵域名摘要可能被字典枚举。不能注入生产 Admin Token、Device token、TURN secret、TLS 私钥或离线签名私钥。

### 8.2 公开构建与专用构建

| 变体/作业 | 配置来源 | 允许做什么 |
| --- | --- | --- |
| 普通 PR、fork、CodeQL、公开 CI | 假配置或空配置；有效测试 pin 来自本地测试证书 | 同一套生成/加载/校验代码，测试全部逻辑；不接生产中心 |
| 普通无配置构建 | 无专用配置 | 局域网能力、可信 QR 配置入口；没有中心配置时不访问隐藏默认端点 |
| 经批准的专用打包 | Environment Secrets | 注入真实配置，生成并验证 APK；不把真实值送回公开测试作业 |

拟在 `android/app/build/generated/` 下生成非源码配置资产，再打入 APK；真实配置不写源码目录、tracked resource、Manifest 或公开 `gradle.properties`。本方案选择运行时共享 OkHttp 工厂，因此不依赖静态 NSC；非敏感的 Manifest 声明本身不是秘密，但任何新增声明仍须在实施范围中列明。优先避免把真实 URL 写入易被编译器错误回显的 Java/Kotlin 源文件。生成路径应被构建系统正确声明为输入/输出，但敏感变体禁用跨信任边界缓存。

当专用打包标志启用时，缺少任一必需配置、占位域名、重复/无效 pin、origin 不合法均在构建前失败，只输出固定错误码。不能悄悄变成普通可发布 APK；假端点不能成为生产 fallback。

配置生成不使用 Base64 或“APK 内置 AES key”作为保密承诺。真实值在 GitHub Secret 存储、runner 临时文件、APK 和运行中设备上有不同暴露边界，需分别控制。

### 8.3 信任与触发边界：不要求先合并 main

公开 PR 作业永远不获得新域名 Secrets。默认禁止 `pull_request_target` 检出 PR 代码，也不从 `workflow_run` 消费未审 PR 工件后执行。

专用预览打包应由**受保护的可信编排工作流**发起，Environment 配置审批人及受限 workflow ref，并明确允许的不可变 source SHA：

- 必须能对 PR #84 的已审核、尚未合并 SHA 打包；不能把“必须先合并 main 才能获得 Secrets”作为验收前提。
- Environment 的 workflow ref 限制不等于源代码 SHA 审核。审批记录必须绑定完整 source SHA、构建脚本/插件/依赖与 workflow SHA；检出固定 SHA，不接受审批后移动的 branch/head。
- 无 Secrets 的预检作业先校验 source SHA 为完整 40 位提交 ID、属于指定仓库/PR 的已审核提交，验证所需公开检查通过；将 PR 号、source SHA、workflow SHA 放入审批前可见的 run name/摘要。Environment 作业再次校验同一输入后固定 checkout 该 SHA，不接受任意自由 ref、审批后替换 SHA 或仅凭作者名称判定受信。摘要不含真实配置。
- 该 SHA 的工作流、Gradle 插件、生成脚本、测试 hook、依赖和子模块都可能外传 Secret。只有完成代码/供应链审核后才可注入，不是“点了 Environment 审批就安全”。
- 若可信编排工作流尚不在受保护 ref 上，应由维护者单独批准引入安全的编排配置，或使用已有可信私有打包仓库；不能利用 PR 特权触发器走捷径。本轮不创建任何此类资源。
- 权限以 `contents: read` 为起点；checkout 不持久化写凭据；第三方 Actions 固定完整 SHA；禁止交互调试 shell、未经批准的网络上传和可疑依赖脚本。
- 新配置 Secrets 只放受保护 Environment，不同时复制到普通 repository secrets。既有签名密钥是否迁移 Environment 是单独审批范围；不假定目前所有签名入口已经隔离。

未审代码不得以“需要测试真实域名”为理由接触 Secret。绝大多数验证用假配置/本地 TLS 完成；真实端点检查只在已审 SHA 的受控作业做必要最小连接，不触发真实短信或用户数据读取。

### 8.4 日志、缓存和产物

- 禁止 `set -x`、输出 env、打印请求 URL/原始异常、Gradle debug/info/build scan；不把真实值放进 `-P`/命令参数。
- 敏感构建工具的 stdout/stderr 先收集到 runner 本地受限临时文件，不直接流入公开 Actions 日志。成功/失败只输出固定状态码、非敏感计数和允许的 SHA；原始诊断不上传。这样比“先公开日志再扫描”更能阻止泄露。
- 首版不提供公开或私有原始日志自动回传：失败先用唯一 canary 假配置在同路径重现，辅以固定阶段/错误码定位。必须查看真实原始诊断时，另行批准私有受控诊断流程与保留期，不因排障临时上传日志工件或启动交互调试。
- GitHub Secret masking 与派生值 `add-mask` 仅作补充，不能依赖其覆盖转义、URL 编码、大小写、拆分值等所有形式。
- 运行期同样使用固定错误码，例如 `CENTER_TLS_PIN_MISMATCH`、`CENTER_AUTH_REQUIRED`；不记录 OkHttp 原始异常消息、cause 链、证书 subject、URL、pin 或未脱敏的崩溃报告。现有 `ApiClient.request/requestWithToken` 会把 path 和原始异常交给 `AppLogger.e`，应逐入口整改；控制端及服务端自由文本错误同样不能未经白名单转换直接进入诊断。
- 现有 `ApiClient.requireHttps` 只验证 HTTPS/host 非空，须按第 7.1 节升级为精确 origin/端口/路径约束，拒绝 userinfo、query、fragment 和跨 origin 重定向；不能把旧弱校验当成新方案已具备的控制。
- 敏感作业既不读取也不写入跨信任边界的 build/configuration cache，防止恢复被投毒缓存；禁 Gradle daemon 日志持久化与 build scan，使用独立干净 runner。具体 setup-gradle 开关在实施前按所用版本验证。
- 生成配置和原始日志不进 artifact、SARIF、mapping、合并 Manifest、测试 HTML、缓存、截图或 Job Summary。压缩包必须解包检查，不只扫外层文件名。
- 产物只允许白名单 APK、APK SHA-256、签名校验的脱敏结果和非敏感构建身份。**专用 APK 含域名属于已接受例外**；上传前应确认它不含生产 token、私钥等其他秘密。
- `git archive` 源码包必须从已审核 commit 生成，不能打包工作目录；检查源码包不含生成配置。本轮不对从未检查的历史仓库作“从未泄露域名”保证。
- 清理生成文件、私密原始诊断和临时签名材料；清理步骤不得把其内容回显。runner 销毁不能替代对上传内容的检查。
- APK 是否公开分发须由用户在实施时确认；公开分发不再能保证域名不会由第三方提取并公开，不能以仓库无域名掩盖此限制。

## 9. CodeQL 与注入配置的验证诚实性

查询 `java/android/missing-certificate-pinning` 依赖可静态识别的 URL 与 pin 配置。动态加载 origin/pin 可能不被识别；查询也不一定证明 pinner 真的挂到了实际 client。

因此验收不能是“改为运行时配置后不报”：

1. 不增加闲置的固定域名 `CertificatePinner.add()`，不拆 URL 躲污点源，不排除规则。
2. 公共 CI 使用相同配置生成与加载路径、真实有效的测试证书/pin、相同 HTTP client 工厂；禁止生产专用网络实现与测试实现分叉。
3. 实际 TLS 负向测试必须证明正确域名但错误公钥被拒绝，且业务凭据/信令尚未发送；空 pin、端点无匹配 pin 必须失败。
4. 代码评审确认所有新信令 TLS 请求使用受测 client，不只是某一个 wrapper。移除/绕过 pinner 的变异应使测试失败。
5. GHAS 仍然扫描全部原有规则；若对动态配置存在分析盲点，记录查询局限与运行期证据，而不是把静默写成“工具证明安全”。

## 10. UX、故障状态与授权退出

拟提供“使用现有管理中心辅助直连”入口，显示是否已登录、节点身份是否匹配、是否已授权信令，不展示真实 host 到可公开导出的诊断。

| 状态 | 行为 |
| --- | --- |
| 缺中心配置/尚未注册 | 显示能力限制；保留本地直连，不自动找公共 PeerJS |
| 旧配对仅有公共发现标志 | 显示 `CENTER_SETUP_REQUIRED`/需升级说明；不自动转换为中心信令授权 |
| 有地址但无会话/授权 | 正常登录或请求一次明确授权，不把 hint 当授权 |
| pin/主机名不匹配 | 拒绝连接，不发送凭据，固定错误码；通过可信配置更新恢复 |
| 中心不可用 | 已建立直连通常仍可用；需交换新信令的重连退避，不能保证成功 |
| NAT 无法直连 | 明确失败；仅在另行批准的数据中继方案下提供 TURN 等选项 |
| 信令会话关闭/过期 | 清理临时队列；不主动断开仍合法的 DataChannel |
| 撤销 P2P 配对/业务权限 | 关闭对应通道和会话，按原权限拒绝后续 RPC |
| 只撤销辅助建连授权 | 停止中心信令；是否结束已建直连遵守独立 P2P 权限，不误称撤销了配对 |

重试采用有上限的指数退避与抖动；网络恢复可重新建短信令会话，但不能跳过重新验证、过期会话或新的用户授权要求。

## 11. 兼容性与升级

- 保留既有 P2P 身份 alias、配对根密钥、业务帧和业务权限，不借传输迁移重置 Vault 或重配所有节点。
- 新增受认证能力字段 `center-signaling-v1` 与原生 RTC 支持：绑定注册/会话握手纳入签名，并在配对状态响应中提供等价字段；现有 `PeerRpc.state()`/`StateCollector` 需显式扩展，旧端缺字段按不支持处理。不能把中心返回的无对端认证声明当作对端能力。
- 已持久化的 `publicDiscoveryEnabled=true` 不代表用户同意中心辅助建连。升级后 `PeerService`/`PeerHubGateway` 不再用该字段启动 PeerJS；在启用服务之前做幂等迁移，保留配对密钥，旧标志置为退役状态或忽略，新的 `signalingConsent` 默认为 false。无可信 pin/中心授权时保留 LAN 并显示 `CENTER_SETUP_REQUIRED`，需要用户一次明确动作；迁移失败也不能再次启动旧发现路径。
- 新中心辅助路径要求双端均支持，旧端不足时明确要求升级，不回退未 pin PeerJS。
- 旧配对 QR 继续按既有格式解析，但 origin hint 不自动变成可信 pin/中心授权。需要 pin 的新 QR 描述版本化，双端签名应绑定其描述摘要；不能改变未升级旧端的派生语义而假称互通。
- 原生/旧引擎在测试中可验证底层 RTC 互通，但不因此在生产保留旧 WebView 网络路径。升级窗口的公网能力限制应公开说明。
- 服务端新增信令表和路由应是增量的；旧短信/OTA/管理 API 不变。任何 DB 迁移/生产部署仍需备份、回滚方案和另行授权。
- pin 信任、中心能力和服务器版本未满足时停止启用新功能；服务端先部署兼容能力、客户端后启用，不让一侧先升级造成隐式权限变更。

## 15. 构建身份、证据与发布门禁

专用注入会使 APK 不同于假配置 CI 的 APK，因此必须记录：source SHA、可信 workflow SHA、依赖校验集合、配置 schemaVersion、非敏感 configId、最终 APK SHA-256、签名身份和实际测试状态。不能把“同 SHA 的另一份 APK 测过”说成这份专用 APK 已测。

同源假配置完整 CI + 专用 APK 的安装/配置加载/无副作用 smoke test 是首版最低组合。真机、公网测试、证书轮换演练和未运行项目逐项标明；不因构建通过就宣称所有安全风险消失。

最新聚合 CodeQL 的活动告警应对应最终 source SHA/PR merge analysis，旧兼容扫描类别的残留与真正活动项分开记录。清理旧类别属于单独核准事项，不得借此隐藏活动告警。

## 16. 回滚与未满足时的安全行为

- 数据库增量设计先保留旧业务路径，服务器回滚不得删除旧用户数据；部署前备份，禁止在本轮执行迁移。
- 新 RTC/中心信令若不能满足验收，关闭该新增功能、保留仍安全可用的局域网与既有独立授权业务能力；不重新开启未 pin PeerJS 或自动转业务 Relay。
- pin 事故恢复走可信应用更新/QR；已泄露域名不能靠删除日志或重新加密“撤回”，需按事件流程处理。域名知悉不应授予访问权限。
- 错误授权修订要撤销会话/队列，不能只隐藏 UI。对不确定是否执行的短信请求遵守原幂等/状态查询机制，不重发生成新 commandId。

## 17. 实施前必须核实的检查点

以下是明确的开工/上线门禁，不是默认已经成立的事实；确认时只反馈是否满足，不把真实值写回本文。

1. 控制端是否已拥有合法中心会话和目标节点权限；独立 P2P workspace 缺会话时的正常登录入口是否可复用。
2. 既有生产部署有几个 TLS 安全表面，在哪里终结 TLS（反向代理/CDN/源站），是否能控制实际被客户端看到的当前/备用公钥。
3. 实际续期工具的 key 轮换行为，是否能安全预置 backup 并在到期前报警；不满足则不能上线 pinning。
4. 本仓 Environment 审批/分支保护的实际可用性及维护人；可信编排 ref 与已审核未合并 SHA 的打包路径。
5. 专用 APK 的分发范围，用户是否接受域名可被安装者提取；真实端点 smoke test 的单独授权。
6. 原生 AAR 的供应链、ABI/页大小/性能，测试工具安装预算及可用真机；本机缺 Gradle/Android SDK 等限制不能写成测试通过。
