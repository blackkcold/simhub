## Pinning honesty notes

- `SecureHttp.pinned(...)` throws `OriginRejected` unless the request origin is the exact canonical origin the trusted description pins for that role, and `PinMissing` unless at least two pins are configured. OkHttp performs no pin check for a host with no pinner entry, so that origin gate is what prevents a silent unpinned request.
- Derived clients (pinned and timeout variants) all come from one base instance, so there is one connection pool and no idle second client. That is only safe because OkHttp keys pooled connections on `Address`, and `Address.equalsNonHost` compares the `certificatePinner` field: verified by disassembling the `okhttp 5.3.2` classes this project actually resolves (`javap -c okhttp3.Address`), where offset 119–126 compares `certificatePinner`. A pinned client therefore cannot inherit a connection opened by the unpinned client, and two clients with different pin sets cannot share one either.
- The pinned-client cache is keyed on role, origin **and the pin set**, and the timeout-variant cache is keyed on object identity rather than an identity hash. Both matter: reusing a client across a key rotation, or a hash collision, would hand back a pinner that has no entry for the host being contacted, which OkHttp treats as "nothing to check". `SecureHttpTrustTest.keysThePinnedClientOnThePinSetSoRotationCannotReuseTheOldPinner` holds that line, and a mutation study confirms each guard fails the suite when removed (recorded in `docs/p2p/ACCEPTANCE.zh-CN.md`).
- The negative behaviour is covered by JVM tests against a real TLS handshake (`SecureHttpTrustTest`): the correct pin is accepted; a valid chain with the wrong pin fails with the fixed code `CENTER_TLS_PIN_MISMATCH` **before any HTTP byte or credential is written**; an empty or single pin set is refused; a redirect to another origin is returned to the caller and never followed.
- A trusted description may be absent (a plain build, or an installed legacy enrollment). In that case the platform trust chain is used exactly as before, the new auxiliary path stays blocked with `CENTER_SETUP_REQUIRED`, and there is no silent trust-on-first-use migration. When a description *does* exist for a role, a request to a different origin is refused rather than sent unpinned.
- CodeQL's `missing-certificate-pinning` query resolves statically identifiable URLs and pins, so a runtime-loaded description can fall outside its analysis. This document therefore reports the query limitation rather than claiming tool-verified safety; the runtime evidence above is the primary evidence.

## Additional CI integrity correction

The earlier `android-sandbox` error annotation was from an **optional GitHub PR comment**, not from the Android instrumentation suite: the logs included `OK (12 tests)` followed by `HTTP 403 Resource not accessible by integration`. The workflow now writes the validated APK link into GitHub Job Summary and removes unused `issues: write` permission. The `simhub-p2p-tested-package` artifact is uploaded only when the test job succeeds.

## Release gates

1. Verify **the GitHub Advanced Security aggregate CodeQL check**, not just the successful CodeQL workflow. Record the exact active alerts and any decisions made by authorized security reviewers. Legacy-category residue must be listed separately from genuinely active findings.
2. Verify standard CI, OTA, Android preview and emulator tests on the **same latest commit**.
3. Verify independent real-device P2P behavior: carrier NAT differences, sleep/network changes, local unlock on API 29 vs 30+, and Relay-first P2P-backup idempotency.
4. Deliver only the corresponding head SHA APK and checksum. Remain in draft and do **not** merge into `main` without user acceptance.
5. `docs/p2p/ACCEPTANCE.zh-CN.md` lists each design acceptance item with its honest current status; items marked `not-run` or `gated` are not covered by the evidence above.
